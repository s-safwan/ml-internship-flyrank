Ranking Pages for Refresh: Machine-Learning Content Opportunity Scoring from Search Visibility Data

Author: Syed Safwan Hashmi • Lane: Refresh / Content Opportunity Scoring • Dataset: FlyRank Warehouse Sample (fact_content_daily_performance, month=2026-03 partition)
0. Abstract
Digital publishers face severe organic traffic stagnation and need to systematically identify which decaying pages possess the active potential to capture clicks if refreshed. To answer this, we analyzed a 30,000-row sample of daily page-level telemetry drawn from a single mid-panel month (March 2026) of the 79-million-row FlyRank warehouse. We trained a Random Forest classifier on physical visibility signals and evaluated it alongside a heuristic baseline using strict 5-fold grouped cross-validation. The model outperformed the rule-based baseline on both metrics — precision of 0.714 ± 0.019 versus the baseline's 0.695 ± 0.034, and accuracy of 0.748 ± 0.013 versus the baseline's 0.583 ± 0.014. This output is structured as an actionable decision-support playbook — a ranked queue blending model probability with a transparent visibility rule, carrying a reason code and confidence label per page — to help prioritize human editorial review.
Model & Analysis Card
What it is
A Random Forest binary classifier (has_clicks) blended with a transparent visibility rule into a single ranked queue.
What it's for
Prioritizing which of thousands of existing pages an editor should review first — for refresh, expansion, or no action — under limited editorial capacity.
What it is not
Not a causal model. Not a guarantee a refresh recovers traffic. Not validated across seasons, algorithm updates, or months beyond March 2026.
Where it breaks
(1) High-volume, naturally zero-intent generic queries produce false positives. (2) ga4_sessions/scroll_events are measured in the same window as the label and may partially echo it rather than independently predict it — see Limitations. (3) The 3-tier action bucketing itself has not been separately scored against ground truth; only the underlying binary classifier was validated.

1. Problem Framing

For content teams managing large portfolios, simplistic heuristic filters (e.g., "refresh all pages ranking on page 2") create either too many false positives or miss thousands of viable opportunities. The unit of analysis is the daily page. The cost of a wrong call is wasted editorial labor on dead pages. This project builds a quantitative classification model to answer a specific operational question, matching Lane 2's brief: Which pages should be reviewed first for refresh, expansion, or monitoring? Data and ML automate this triage at a scale humans cannot process manually.

2. Data

We utilized a 30,000-row sample from the FlyRank warehouse's fact_content_daily_performance table, month=2026-03 partition, filtered to rows with ga4_data_available IS TRUE. The full release (FlyRank/internship-warehouse on Hugging Face, gated, instant approval) is ~79 million rows across ~17 months; we work from one representative month for iteration speed. To ensure strict public safety and avoid leakage, pseudonymous entity IDs (client_hash_id and content_hash_id) were deliberately retained exclusively for cross-validation grouping and never used as predictive features. Sibling target-leakage columns (specifically sessions_organic) were permanently excluded from the training set. The observed click base rate in this sample is 43.7%.

Extraction note: rows were pulled with a deterministic ORDER BY content_hash_id LIMIT 30000 rather than an unordered LIMIT, so the same 30,000 rows are selected on every re-run — this is what makes the reproducibility claim in Section 9 accurate. Note that this specific 30,000-row slice (ordered by content_hash_id) has a somewhat different base rate (43.7%) than an earlier, non-deterministic pull of the same table (49.5%) — a reminder that even a fixed-size sample's composition depends on which rows are selected, which is exactly why we fixed the ordering.

Leakage check performed: we tested the behavioral features directly with a drop-feature audit rather than excluding them on assumption alone. A model trained with scroll_events and ga4_sessions scored 0.742 accuracy on a held-out split; a model trained without them (impressions and position only) scored 0.740 — a drop of only 0.2 percentage points. Because the score did not collapse, we treat the retained behavioral features as predictive rather than a hard leak, while flagging the residual window-overlap concern in Limitations. sessions_organic, which mirrors the click-based label almost exactly, was excluded outright as a confirmed sibling-leakage risk.

3. Baseline

We established a transparent business heuristic baseline (Impressions > 500 AND Position > 10) representing the standard rule an SEO manager might build first. It is a fair comparison because it uses a subset of the same visibility metrics available to the model (gsc_impressions, gsc_avg_position), with no access to information the model doesn't also have. On the grouped validation split, this rule achieved a mean precision of 0.695 ± 0.034 and a mean accuracy of 0.583 ± 0.014 across 5 folds, only modestly outperforming the 43.7% base rate on accuracy.

4. Methodology & Model

We framed the task as binary classification, defining the target proxy in one sentence: Does the page register at least one organic click during the observation window (has_clicks = True)? We selected a Random Forest Classifier because it captures non-linear thresholds in visibility metrics without requiring extensive feature scaling. The exact feature list includes gsc_impressions, gsc_avg_position, ga4_sessions, and scroll_events.

Hyperparameters: n_estimators=100, max_depth=5, random_state=42, held fixed across every evaluation reported below. These were set by reasonable convention (matching values used consistently across our earlier exploratory notebooks), not selected via a hyperparameter search — we did not sweep a range or optimize against a validation metric, and we say so here rather than implying a tuning process that didn't happen.

Assumption made explicit: we assume the March-2026 snapshot's relationship between visibility signals and click behavior is stable enough to generalize to nearby months. We do not assume it generalizes across a full algorithm update or a seasonal shift — see Limitations below.

5. Results

To prevent domain memorization, both the baseline and the model were evaluated simultaneously inside a strict 5-Fold Grouped Cross-Validation (GroupKFold) keyed on content_hash_id, so no content item's rows appear in both train and test. This performs 5 training runs per strategy (10 total fits).

Ranking metrics: Precision@20 = 0.950, Precision@50 = 0.960, Precision@100 = 0.960, Average precision = 0.789, Recall @0.5 = 0.701, Base rate (naive) = 0.437. The gap between Precision@20 (0.950) and the overall triage precision (0.714) shows the model is far more reliable at the very top of the ranking than across the full queue — exactly the property a capacity-limited editorial team needs.

Error Analysis: The Random Forest model outperforms the baseline on both metrics reported here — accuracy (0.748 ± 0.013 vs. 0.583 ± 0.014) and triage precision (0.714 ± 0.019 vs. 0.695 ± 0.034) — each with modest variance across folds, indicating a stable, reproducible improvement over the heuristic rule rather than a lucky split. The primary remaining errors are false positives on high-volume generic queries with naturally zero-click intent, which the model misinterprets as opportunity.

6. Interpretation

The feature importance analysis confirms the model relies heavily on pure physical visibility (Impressions and Position) to drive its predictions, with weaker reliance on engagement signals (GA4 sessions, scroll events). A directional finding here is that physical visibility appears to matter more to the model than prior session depth — this is observed in this sample and should not be read as a general SEO law.

7. Limitations & Honest Framing

This is an observational decision-support tool, not a causal forecasting engine. We did not run an experiment, so we make no claim that refreshing a flagged page will cause its traffic to recover — only that the page shows the pattern of pages that currently capture clicks.

Same-window feature/label overlap: ga4_sessions and scroll_events are measured in the same window as the has_clicks label. A page cannot easily register an organic GA4 session without a click having occurred first, so these features may partially echo the label rather than independently predict it. Our drop-feature test (Section 2) showed only a 0.2-point accuracy change when they were removed, which is reassuring but not conclusive — gsc_impressions and gsc_avg_position alone already carry most of the signal and could be masking a smaller circularity effect. Future work should test the model on a strictly earlier feature window predicting a strictly later label window.

The 3-tier action playbook (Section 8) has not been separately validated: only the underlying binary classifier was scored with grouped cross-validation. The Hold/Refresh/Expand thresholds are directional heuristics layered on top of a validated model, not a validated classifier in their own right.

The model was trained and evaluated on a single month's data (March 2026), with hyperparameters fixed by convention rather than searched (Section 4). We have not tested whether performance holds across seasons, algorithm updates, or other months, and we make no claim that it does. We also do not claim to have modeled or predicted Google's ranking algorithm — only observed associations between visibility signals and click behavior within this portfolio.

8. Ranked Recommendations

The final queue blends each page's out-of-fold model probability (70% weight) with a normalized visibility score (30% weight), aggregated to one row per page, then buckets pages into a 3-tier action playbook a FlyRank editor can use immediately. Every row carries a reason code and a confidence label (high/medium/low) derived from the model probability and impression volume:

  1. REFRESH_FOR_CTR: High impressions (>1,000) at positions beyond 10 (page two or later, no upper cap). Action: Optimize meta descriptions and titles.
  2. EXPAND_CONTENT: Strong rank (Top 10) but low GA4 sessions (<50). Action: Expand content depth and multimedia.
  3. HOLD: Everything else. Do not touch.

9. Reproducibility

To reproduce: open work/notebooks/capstone.ipynb in Google Colab via the badge in the repository README, paste your own free Hugging Face read token when prompted (after requesting access to the gated dataset), then Runtime → Run all. Repeat for work/notebooks/w07_action_playbook.ipynb to regenerate the ranked queue.

Infrastructure: Google Colab, free-tier CPU runtime, no GPU used. The full pipeline (data pull, 5-fold cross-validation, and queue export) completes in a few minutes end-to-end on this infrastructure — no specialized hardware is required to rerun this study.

Training runs: 5 folds × 2 strategies (baseline, Random Forest) = 10 fits per full evaluation pass, plus 5 additional out-of-fold fits for the ranked-queue probabilities in Section 8.

Seed: random_state=42, fixed across every model fit in this study.

This entire study is reproducible from the committed notebooks: the deterministic extraction query, the grouping logic, and the random seed are all committed in the public Jupyter notebooks in the project repository, including the leakage-check audit and the out-of-fold queue-building logic.
